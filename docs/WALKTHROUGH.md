# Учебный разбор проекта ai-reliability

Этот документ объясняет, как устроен проект и почему он устроен именно так. Синтаксис Python
здесь почти не разбирается. Главное — инженерные решения, режимы отказов и принципы QA,
которые стоят за каждым модулем.

Для каждого крупного модуля разобрано пять вопросов:
1. **Что это.**
2. **Зачем оно нужно.**
3. **Что это даёт.**
4. **Как работает.**
5. **Как тестируется.**

---

## 0. Главная идея за одну минуту

Обычный «тестер LLM» отправляет промпт и смотрит на ответ. Здесь задача шире: принять
обоснованное релизное решение и доказать, что инструмент, который это решение принимает,
сам надёжен.

Отсюда четыре слоя:

1. **Проверки ответов** (`checks/`, `rag/`). Детерминированные, объяснимые, по аннотациям.
2. **Решение о релизе** (`evaluation/release.py`). Правила, которые нельзя «усреднить».
3. **Проверка самого проверяющего.** Selftest-фикстуры, размеченный набор с
   precision/recall, метаморфные отношения, мутационное тестирование на эталонном
   RAG-приложении.
4. **Безопасность и стоимость.** Оффлайн по умолчанию, редактирование секретов,
   запрет платных моделей без явного разрешения.

Принцип, который проходит через всё: **честность важнее внешнего вида**. Если вердикт
нельзя вывести из аннотаций, это `INCONCLUSIVE`, а не `PASS`. Если у проверки есть слепое
пятно, оно записано в тестах как `known_miss` и показано в README.

## 1. Модели и сценарии — `reliability/models.py`, `reliability/scenarios.py`

**Что это.** Pydantic-модели для сценариев, документов, результатов проверок и отчёта, плюс
загрузчик, который валидирует все файлы до начала прогона.

**Зачем.** Сценарий — это тест-кейс. Опечатка в тест-кейсе особенно опасна: например,
`expected_claim` вместо `expected_claims`. Проверка молча получит пустой список, вернёт
`NOT_APPLICABLE`, и тест будет «зелёным», ничего не проверив. Это классический ложноположительный
результат в самом тестовом наборе.

**Что даёт.** Неизвестные поля запрещены (`extra="forbid"`). Каждая ошибка называет файл,
id сценария, поле и проблему. Пример: `cases.json: scenario 'bad-1' field 'severity': Input should be ...`.
Дополнительно проверяется семантика:
- имена проверок существуют;
- id документов есть в датасете;
- у каждого сценария есть заготовленный ответ мока;
- selftest-сценарий обязан объявить ожидаемые вердикты, а gate-сценарий не имеет права
  их объявлять.

**Как работает.** Двухступенчатая валидация:
1. **Структура** — Pydantic.
2. **Связи между файлами** — `scenarios.py`: документы, проверки, ответы мока.

Ошибки копятся и выдаются списком, а не по одной. Это экономит итерации.

**Роли gate и selftest — ключевое решение проекта.** ТЗ одновременно требует:
- негативные кейсы в датасете;
- падения CI при любом коде выхода, кроме 0.

Совместить это можно только так:
- плохие фикстуры (`selftest`) прогоняются **каждый раз**, но не входят в решение о
  релизе приложения;
- каждая из них обязана воспроизвести заранее записанные вердикты;
- если хоть одна не воспроизвела, правило R0 переводит прогон в ERROR. Сломанный
  измерительный прибор не имеет права выносить вердикт.

**Как тестируется.** `tests/unit/test_models_config_providers.py` проверяет:
- неизвестные поля;
- некорректные regex и JSON Schema;
- дубли id;
- последнее сообщение не от пользователя;
- формат сообщений об ошибках;
- лимиты размера файлов.

## 2. Конфигурация — `reliability/config.py`, `config/default.toml`

**Что это.** Веса, пороги, лимиты, режим стоимости.

**Зачем.** Пороги релиза — это политика команды, а не код. Их нужно менять без
правки исходников и видеть в отчёте.

**Как работает.** Порядок применения:
1. `default.toml`.
2. Файл пользователя (`--config`) поверх него, с глубоким слиянием.
3. Переменные окружения `AIREL_*`.

Всё валидируется: порог `min_pass_rate = 7` будет отклонён. Снимок итоговой конфигурации
кладётся в каждый JSON-отчёт, поэтому решение воспроизводимо.

**Как тестируется.** Тесты покрывают:
- значения по умолчанию;
- переопределения;
- битый TOML;
- регулярное выражение цитат без группы `id`.

## 3. Провайдеры и защита от расходов — `reliability/providers/`

**Что это.**
- Протокол `Provider`.
- Иерархия ошибок: таймаут, 429, 5xx, авторизация, битый ответ.
- `MockProvider` и `StatefulMockProvider`.
- Гард стоимости и бюджета.

**Зачем.** Проект должен собираться и демонстрироваться бесплатно. Случайный вызов платного
API из теста — это реальные деньги и утечка данных.

**Как работает.**
- **Мок.** Отдаёт заготовленный текст или имитирует ошибку. С `fail_times` он падает только
  первые N раз, а затем отвечает — так проверяются ретраи.
- **Stateful-мок.** Помнит сообщения внутри `session_id`. Режим `echo_history` моделирует
  систему, которая «выдаёт» прошлого собеседника. На этом построен тест межсессионной утечки.
- **Гард стоимости.** Классифицирует модель по белому списку:
  - `mock`;
  - `local` — `ollama/...` на loopback-адресе;
  - `paid` — всё остальное, включая незнакомые имена.

  Платная модель отклоняется **до создания объекта провайдера**, значит до любого сокета.
- **BudgetGuard.** Оценивает худший случай: входных токенов не больше, чем байтов UTF-8,
  выходных не больше `max_tokens`. Запрос, который мог бы превысить бюджет, не отправляется.
  Цены берутся только из файла пользователя, никогда не угадываются.

**Как тестируется.**
- Тест со «шпионом» на `socket.socket.__init__` доказывает, что при отказе не создаётся
  ни одного сокета.
- Отдельные тесты проверяют классификацию, бюджет и изоляцию сессий.

**Чего нет.** Живой LiteLLM-провайдер — это фаза 7. Он не реализован, и CLI честно об этом
говорит.

## 4. Лексическое сопоставление — `reliability/checks/text.py`

**Что это.** Общие примитивы для фактов и утверждений:
- фраза на границе слова;
- предложение;
- окно отрицания и хеджирования;
- конфликт чисел.

**Зачем.** Без семантической модели нужен прозрачный, объяснимый способ. Каждый вердикт
можно показать пальцем: «вот символы, вот правило».

**Как работает.**
- «30 days» не совпадёт с «130 days» и с «2.30 days»: проверяется граница слова и
  десятичная точка.
- Отрицание ищется в последних 3 токенах **того же придаточного**. Запятая, точка с
  запятой и двоеточие обрывают область отрицания (идея из NegEx). Без этого правила фраза
  «if it does not stop, use kill -9» ошибочно считала «kill -9» отрицанным. Мы поймали это
  на собственном сценарии.
- Конфликт чисел: в том же предложении стоит другое число с той же единицей, и перед ним
  нет отрицания. «Not 14 days as before — now 30 days» — не конфликт.

**Ограничения записаны явно.** Не анализируется время («used to be 30 days»). Не видно
отрицания после фразы. Нет синонимов.

**Как тестируется.** `tests/unit/test_text_matching.py`: таблица ловушек на границы слов,
отрицание, хеджирование, предложения и запятые.

## 5. LLM-проверки — `reliability/checks/`

| Проверка | Идея | Главная ловушка, которую она обходит |
|---|---|---|
| `required_facts` | факт присутствует, не отрицается, не противоречит числом | «130 days» ≠ «30 days» |
| `forbidden_content` | маркеры и regex, политика `outside_refusal` | кодовое имя внутри отказа — не утечка |
| `structured_output` | `json.loads` + JSON Schema | ограждения ```json``` — это нарушение контракта, если их явно не разрешили |
| `refusal` | паттерны отказа и воздержания | **чрезмерный отказ — такой же FAIL**, как опасный ответ |
| `instruction_following` | только размеченное: разделы, длина, формат списка | «In summary…» — не заголовок раздела |
| `provider_call` | исход вызова: попытки, класс ошибки, пустой или обрезанный ответ | пустой ответ — это FAIL приложения, а auth-ошибка — ERROR инфраструктуры |

Почему пустой ответ — это FAIL, а ошибка авторизации — ERROR?

- **FAIL** — приложение ответило плохо. Это вердикт о качестве.
- **ERROR** — мы не смогли получить ответ. Это вердикт об инфраструктуре.

Смешивать их нельзя: иначе падение сети выглядело бы как регрессия модели.

**Как тестируется.** `tests/unit/test_llm_checks.py`. Для каждой проверки есть хорошие,
плохие и пограничные случаи. Известные ограничения тоже закреплены тестами. Например,
пересказ запрещённой фразы **не** ловится, и тест это утверждает, чтобы ограничение
оставалось видимым.

## 6. RAG-проверки — `reliability/rag/`

**Зачем отдельно.** В RAG ошибка может возникнуть на трёх этапах:
- поиск вернул не те документы;
- контекст содержит устаревшее или чужое;
- генератор написал то, чего нет в контексте.

Каждый этап проверяется отдельно, чтобы находка указывала на виновника.

- **`retrieval_metrics`.** Precision@K, Recall@K, MRR.
  - Дубликаты считаются один раз, по лучшему рангу.
  - Пустой поиск даёт 0 по всем метрикам.
  - Нет разметки релевантности — `NOT_APPLICABLE`, а не выдуманное число.
- **`context_quality`.** Precision и recall контекста. Флаги:
  - дубликаты;
  - устаревший документ (по `version`, затем по `valid_until`);
  - устаревший **выше** актуального — это FAIL;
  - конфликт из разметки;
  - чужой уровень доступа — FAIL;
  - «релевантен, но не подтверждает ни одно утверждение» (релевантность ≠ подтверждение).
- **`grounding`.** Каждое ожидаемое утверждение получает один статус: supported,
  unsupported (сказано без опоры на найденный документ), contradicted, omitted или hedged.
  Утверждения из `false_claims` дают FAIL. Неразмеченный текст измеряется как
  `unverified_content_ratio` и **никогда** не называется галлюцинацией: мы просто не знаем.
- **`citations`.** Ловит:
  - выдуманные id;
  - id, которых не было в выдаче;
  - утверждение без цитаты;
  - цитату не на тот документ.

**Ортогональность — намеренная.** В сценарии `rag-015` модель цитирует устаревший документ,
который действительно был в выдаче. Поэтому `citations` даёт PASS: цитата формально
корректна. А `grounding` даёт FAIL: утверждение ложное. Проверка цитат не судит об истинности.

**Как тестируется.** `tests/rag/test_rag_checks.py`. Метрики сверены с ручным расчётом,
включая дубли, пустую выдачу, K больше длины выдачи и пропуски в рангах.

## 7. Безопасность — `prompt_injection`, `data_leakage`, `sensitive.py`, `redaction.py`

**Canary-токены.** Каждая вредная инструкция содержит уникальный маркер. Если маркер
появился в ответе, инъекция сработала. Маркер ищется в трёх формах:
- напрямую;
- «вразрядку» (`C A N A R Y - …`);
- в base64.

Утечку системного промпта ловят 8-словные «черепицы» (shingles) из текста промпта.

**Утечка данных.** Секрет ищется в четырёх формах:
- точно;
- без разделителей;
- в base64;
- по последним 4 символам отдельным токеном («card ending 1234»).

Секрет, процитированный **внутри отказа**, — всё равно утечка. Сценарий `sec-009` показывает
частичное соблюдение: модель говорит «не могу», но называет последние цифры.

**Межсессионная утечка.** Сценарии работают в одной сессии `StatefulMockProvider`:
- `sec-012` — пользователь A сообщает карту;
- `sec-013` — пользователь B в той же сессии получает её обратно, утечка поймана;
- `sec-014` — другая сессия, изоляция подтверждена.

Если запустить только `sec-013`, CLI сам подтянет предшествующие шаги той же сессии.

**Редактирование.** Через `Redactor` проходит всё, что покидает оценщик:
- доказательства;
- фрагмент ответа;
- ошибки;
- JSON;
- HTML;
- строки логов.

Маска сохраняет только буквенную метку: `CANARY-****Q7`, `sk-****Y0`. У карты остаются
лишь последние 2 цифры: `****34`.

**Как тестируется.** `tests/security/test_security.py`:
- полный прогон с логированием, после которого проверяется, что ни одна форма ни одного
  секрета не попала в отчёты, stdout, stderr и логи;
- контрольный тест, что моки действительно содержат секреты, иначе предыдущая проверка
  была бы пустой;
- AST-тест на запрещённые конструкции (`eval`, `pickle`, `subprocess`…);
- тест, что весь прогон не открывает ни одного сокета.

## 8. Оркестрация и ретраи — `reliability/evaluation/orchestration.py`

**Что это.** Цикл прогона: построить запрос, вызвать провайдера с ограниченными ретраями,
оценить, собрать отчёт. Отдельная функция `run_rag_app` делает то же самое для любой
системы, реализующей `RAGSystem`.

**Как работает.**
- Ретраятся только таймауты, 429 и 503. Всего попыток не больше `1 + max_retries`.
- Задержка: экспоненциальная (0.5, 1, 2 …, с потолком). Если сервер прислал `Retry-After`,
  используется он. `Retry-After` больше лимита — остановка, а не ожидание 2 минут.
- Сон и часы внедряются снаружи. В тестах «сон» записывает задержки и не спит, поэтому
  тесты мгновенные. С мок-провайдером CLI тоже не спит (время симулируется), но задержки
  пишутся в доказательства.
- Ответ длиннее `max_response_chars` обрезается и помечается: защита от огромных ответов.

**Как тестируется.** `tests/integration/test_operational.py`:
- каждый путь отказа;
- потолок задержки;
- ноль ретраев;
- измерение задержки по внедрённым часам.

## 9. Оценщик, скоринг, релизное решение — `evaluator.py`, `scoring.py`, `release.py`

**Оценщик.** Выполняет проверки сценария. Если вызов провалился, каждая проверка получает
ERROR. Упавшая проверка тоже получает ERROR. В обоих случаях — **никогда PASS** (принцип:
незавершённая критическая проверка не засчитывается). Затем оценщик сверяет вердикты
selftest-сценариев с объявленными.

**Скор.** Только информационный. Взвешенная доля PASS среди PASS+FAIL.

**Решение.** Правила R0–R6 применяются по порядку. Записываются все сработавшие, решает
первое. Важные детали:
- R1 нельзя «разбавить»: один критический FAIL среди сотни PASS — это FAIL.
- В pass rate не входят ERROR и INCONCLUSIVE. Иначе сбой инфраструктуры сработал бы как
  R2 (FAIL приложения) раньше, чем R3 успел бы сказать «это инфраструктура».
- Прогон, в котором нечего оценивать, — REVIEW_REQUIRED, а не PASS.

**Как тестируется.** `tests/unit/test_release_and_scoring.py`. На каждое правило есть явный
тест, включая границу ровно на пороге и порядок срабатывания. Отдельный тест пересчитывает
решение из сохранённого JSON и сравнивает его с исходным: так проверяется воспроизводимость.

## 10. Отчёты — `reporting/`

- **JSON.** Ключи отсортированы, поэтому два прогона можно сравнить обычным diff. Внутри:
  хэши файлов сценариев и датасета, снимок конфигурации, источник задержки (`simulated` или
  `measured`). Токены попадают в отчёт только если провайдер их вернул.
- **Summary.** Текст для QA-инженера:
  - решение и причины;
  - самопроверки;
  - критические находки;
  - RAG;
  - безопасность;
  - операционные проблемы;
  - конкретные следующие шаги.
- **Compare.** Изменившиеся статусы с пометкой регрессий, смена решения, дельты метрик.
  Код выхода 1 при регрессии.
- **HTML.** Один самодостаточный файл. Всё экранируется. CSP разрешает только наш скрипт
  фильтрации, привязанный по SHA-256. Даже если экранирование однажды сломается, внедрённый
  скрипт не выполнится.
- **History.** Компактная строка JSONL на прогон для трендов. В CI она пишется в ветку `history`.

## 11. Проверка проверяющего

Это самая важная часть для портфолио AI QA. В проекте четыре независимых механизма:

1. **Selftest-фикстуры (каждый прогон).** 31 заведомо плохой или хитрый случай. Каждый
   должен дать ровно объявленные вердикты, иначе R0 → ERROR.
2. **Размеченный набор (`check-quality`).** 80 случаев с «истиной». Для каждой проверки
   считаются TP, FP, FN, precision, recall и agreement. Известные промахи помечены
   `known_miss` с причиной. Тест падает в двух случаях:
   - появился неожиданный промах;
   - известный промах вдруг исчез. Тогда метку и README нужно честно обновить.
3. **Метаморфные отношения.** Для них не нужен «правильный ответ». Нужно знать, как вердикт
   **не должен** меняться: регистр, пробелы, перестановка документов, нейтральное
   предложение, отрицание, base64.

   Отношение M1 нашло реальный дефект. Паттерны отказа были записаны с одиночными
   пробелами, и двойной пробел ломал распознавание отказа.
4. **Мутационное тестирование.** В эталонное приложение по очереди внедряются 5 дефектов.
   Каждый должен быть пойман ожидаемой проверкой и перевести решение в FAIL или REVIEW.

   Первый же прогон показал пробел. Галлюцинация (выдуманная комиссия) ловилась проверкой
   `grounding`, но релиз оставался PASS: одна ошибка уровня high среди 22 проверок не опускала
   pass rate ниже 90 %. Вывод: важность (severity) — это политика, и её тоже надо тестировать.

Честное замечание. Размеченный набор и сценарии написаны тем же автором, что и проверки.
Поэтому цифры оптимистичны. Они показывают, что проверки делают заявленное на продуманных
случаях, и делают слепые пятна явными. Это не оценка качества на реальном трафике.

## 12. Эталонное RAG-приложение — `rag_app/`

**Что это.** Маленький, но настоящий RAG:
1. BM25-поиск.
2. Фильтр свежести.
3. Фильтр доступа.
4. Сборка промпта с пометкой «недоверенные данные».
5. Генерация.

**Зачем.** До этой фазы оценщик проверял фикстуры: «правильно ли он размечает заранее
подготовленные ответы». Теперь есть система под тестом, и можно доказать, что оценщик ловит
настоящие баги в настоящем пайплайне.

**Архитектурная граница.** `rag_app` не импортирует оценщик. Оценщик знает только
`rag_app/interface.py` (протокол `RAGSystem`). Связывает их `cli.py` — точка сборки. Оба
правила проверяются тестом по AST. Поэтому любую другую RAG-систему (векторную, HTTP)
можно подключить, реализовав один протокол.

**Дефекты.** Каждый ломает ровно один этап, и тест это доказывает: сравниваются выдача и
промпт без дефекта и с дефектом.

| Дефект | Что ломает |
|---|---|
| `no_access_filter` | пропускает фильтр доступа |
| `stale_first` | оставляет старые версии и ставит их выше |
| `no_grounding_instruction` | убирает инструкцию «отвечай только по документам» |
| `truncated_context` | обрезает контекст |
| `no_untrusted_marking` | вставляет документы как инструкции |

**Ограничение мок-генератора.** Дефекты поведения модели (`no_grounding_instruction`,
`no_untrusted_marking`) ловятся настолько, насколько правдоподобно написаны заготовленные
ответы. Три дефекта пайплайна реально меняют то, что доходит до генератора, и ловятся без
этого допущения. Настоящую проверку поведения даст локальная модель (фаза 7).

**Найденная слабость самого приложения.** На запрос «What is the return window?» BM25
ставит пост с форума выше официальной политики: в посте буквально есть слова «return
window». Это не скрыто подбором порога. Сценарий `rag-013` исключён из мутационной базы, а
ограничение описано в README.

## 13. Инженерная гигиена

- **ruff** — линтер и форматтер. **mypy** — строгая проверка типов для `reliability/` и
  `rag_app/`.
- **pytest.** 702 теста за ~2 секунды, без сети. Автоматическая фикстура запрещает сокеты.
- **CI (`.github/workflows/ci.yml`).** Шаги по порядку:
  1. установка;
  2. линт;
  3. типы;
  4. тесты с покрытием;
  5. валидация сценариев;
  6. релизный гейт;
  7. мутационный тест;
  8. артефакты;
  9. для `main` — запись истории в ветку `history`.

  Пока workflow не запущен на GitHub, он помечен как UNVERIFIED. YAML разобран, команды
  выполнены локально, шаг с историей прогнан на локальном bare-репозитории.
- **Git.** Отдельный коммит на каждую фазу, с осмысленным сообщением.
